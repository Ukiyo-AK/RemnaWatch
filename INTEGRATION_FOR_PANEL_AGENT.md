# Интеграция агента панели

1. Подготовьте Python 3.8+ через deploy/install.sh --install-deps, предоставьте сервису read-only доступ к существующему Xray access.log и отдельный каталог базы с правами только сервисного аккаунта. Xray конфигурация не меняется автоматически. Если access logging выключен, модуль не получит событий; решение о включении и нагрузке логирования принимается оператором отдельно.
2. Скопируйте config.example.json в config.json. Укажите node_id, path, **реальное смещение timezone Xray log** (utc_offset_minutes), inbound tag, точный Xray email и постоянный ID пользователя Remnawave. Это не обязательно email аккаунта панели. Не используйте wildcard, NAT IP или позицию пользователя в списке. Секретные UUID протокола не нужны. Дубли `(node,inbound,email)` запрещены.
3. На основном сервере сгенерируйте отдельный token для ноды (`python -m remnawatch.auth issue-token` или generate_node_credentials()), сохраните node_id/token в защищённой записи панели и вставьте token в auth.token конфига ноды. После запуска `python -m remnawatch --config config.json` проверьте GET /v1/node с Bearer header и сверьте UUID с записью панели. Старый REMNAWATCH_API_TOKEN остаётся fallback при пустом/отсутствующем auth.token; config secret имеет приоритет. Для systemd используйте обычный service account, restart policy и ограничения CPU/IO; Xray не должен ждать этот процесс. Не запускайте несколько экземпляров с одной SQLite базой/источником. Подробный контракт Python/Node.js backend и ротация: [NODE_ENROLLMENT.md](NODE_ENROLLMENT.md).
4. По умолчанию сбор начинается с конца файла. `start_at_end=false` нужен для контролируемого импорта существующего лога. После первого старта применяются сохранённые cursors. Остановите сервис перед изменением user mapping/config, замените mapping целиком и перезапустите. Не переиспользуйте Xray email без контроля границы логов: старые неимпортированные записи могли принадлежать прежнему пользователю. При миграции начинайте с нового файла/cursor или импортируйте старые события под прежним mapping.
5. Панель обращается к документированным GET endpoints с Bearer header. Токен имеет доступ ко всем пользователям этой ноды/сервиса; его нельзя передавать конечному пользователю. Backend панели обязан проверять свои RBAC/tenant права до выдачи истории. Встраивание в существующий API: общий middleware авторизации перед `dispatch`; не публикуйте dispatch напрямую. Не журналируйте domain paths и ответы, отключите кеширование истории. Удалённый доступ защищается TLS proxy.

`domains.enabled=false` выключает сбор; при `purge_on_disable=true` данные удаляются автоматически на старте/очистке. Изменения JSON применяются после перезапуска. Библиотечный Store.set_enabled умеет переключать без рестарта. Автоочистка подробных данных 7 дней, агрегатов 30; сроки изменяются в domains. Удаление файлов логов Xray и backups находится в ответственности оператора.

Для Linux network context добавьте `"network": [{"node_id":"node-1","interfaces":["eth0"]}]`. Сервис должен работать на соответствующей ноде; counters узла не должны маркироваться ID другой ноды. Интерфейсы выбираются явно, polling 5 секунд. Ошибки измерения видны в quality.collector_counters. `network_load` используется для визуального сопоставления activity buckets со скачками, без вывода о причинности или распределения трафика доменам.

Не обещайте пользователю полную историю посещений. Интерфейс панели должен показывать «зарегистрированные соединения», source/confidence, доступные сроки, domain coverage и null для неизвестных данных. История содержит чувствительные сведения: ограничьте экспорт и доступ, согласуйте хранение с политикой оператора.

## Дополнительные источники

В штатной исследованной Xray сборке sniffed domain безопасно не экспортируется универсальным API (см. ARCHITECTURE.md). Не активируйте routeOnly, FakeDNS, sniffing или новые маршруты ради мониторинга; не включайте постоянный debug/info logging.

Для уже существующего безопасного exporter конкретной сборки можно вызвать `correlated_metadata(data, users)` → `store.ingest([event])` внутри доверенного агента. Producer обязан проверить user/connection correlation и точность bytes, передать только whitelist поля. Минимальный контракт: connection_id, node_id, inbound, email, timestamp UTC seconds, domain или destination_ip, protocol, destination_port, source, correlation_verified=true. Optional: client_ip, outbound, exact_connection_bytes. Одна финальная запись на соединение, стабильный ID для retries. Нет ingestion HTTP endpoint. Запрещено передавать raw HTTP headers, paths, cookies, TLS payload или Attributes целиком.

DNS/FakeDNS принимаются только при подтверждённой связи с этим user/connection, без PTR догадок и без shared-cache корреляции. Отдельный адаптер нужно проверить на реальной версии и нагрузке; текущий модуль не выдаёт такие сведения сам.

## Управление и ресурсы

Backend панели может использовать GET /v1/server для характеристик/нагрузки и уведомлений protection.alerts (опрос каждые 10–30 секунд). Показывайте неизвестные metrics как неизвестные. Для действий используйте POST /v1/server/actions с dry_run для просмотра конкретного плана, затем тот же action/params с dry_run=false и уникальным request_id. Следите за job ID через /v1/server/jobs/{id}. Не повторяйте автоматически failed/interrupted update/reboot с новым ID. Оператор должен знать, что reboot/core restart/node update прерывают соединения, а RX policing затрагивает весь NIC.

Управление — opt-in config и host root; default monitoring-only остаётся возможным без root. Windows mutations не поддерживаются. Подключение и deployment описаны в [SERVER_MANAGEMENT.md](SERVER_MANAGEMENT.md). Административный Bearer token нельзя выдавать конечным пользователям; API панели должен отдельно проверять права администрирования сервера. Source API здесь не имеет per-user role, поэтому фильтр user_id не ограничивает права токена.

Ранняя очистка истории при full disk отражается в domain quality.emergency_retention. Пауза по памяти/диску отображается как collection_paused/pause_reasons и не означает deliberate disabled/purge. Для удаления внешних rotated logs задайте только операторские log_directories; активные logs должны обслуживаться logrotate. Защита памяти не является гарантией отсутствия reboot или OOM termination.

## Capabilities, диагностика и live API (Panel 2.7.4 / ALTLINK)

Сначала запросите `/v1/capabilities`: на старом агенте 404 должен выключать только новый UI, а не host monitoring. Не объявляйте unsupported поле нулём. Разделяйте supported/configured/healthy, source unavailable и пустой успешный snapshot. Storage v2 критичность учитывает required и включённость источника; старый log_storage_unavailable доступен через legacy_code/legacy_alerts.

Live source выключен по умолчанию. linux_inet_diag — namespace transport sockets без Xray user/domain correlation. Не подписывайте этот экран «все пользовательские подключения», не превращайте socket в logical stream и не распределяйте user counters. user/inbound filters могут честно давать пустой результат. Tenant/user permissions всегда проверяет backend; фильтр не авторизация. При отображении NIC/bridge выбирайте явное правило, сами rates уже раздельные.

Для replica: полностью прочитайте `/v1/connections/live` с одним snapshot_id, затем используйте его next_cursor в `/v1/connections/changes`. Идемпотентный upsert по connection_id/sequence, tombstones и state-exit transitions обязательны. HTTP 409 требует полного resync, не пропуска событий. Detalи и retention RAM см. [LIVE_DIAGNOSTICS.md](LIVE_DIAGNOSTICS.md). Для точной UUID attribution нужен отдельный доказуемый application exporter; текущий адаптер ничего не угадывает.

CLI strict_user_uuid=true требует Remnawave UUID. При смене mapping непрочитанный backlog старого cursor не приписывается новому пользователю; потеря явно отражается в diagnostic gap. Для controlled import сперва обработайте старый backlog с прежним mapping. Новый сборщик не требует обновления панели/Xray; реальный end-to-end ALTLINK тест и runtime старого image пока не заявлены.
## Контракт 0.2.0 и ALTLINK

Читайте agent_version из аутентифицированного /v1/node отдельно от remnanode_version/xray_version. Сверяйте node_id, service и api_version до сохранения heartbeat. Политика recommended/minimum/channel/updated_at/release_notes/update_instructions задаётся только администратором backend. Не доверяйте node-provided recommended/latest. releases.py даёт parse/compare/validate_policy/status; неизвестные версии и dev/custom builds не объявляются актуальными, отсутствующий/старый heartbeat → stale_heartbeat. SemVer 1.10.0 > 1.9.0. Показывайте build отдельно, warnings/filter/count рассчитывайте на backend. Не запускайте update при проверке версии.

Новый installer не заменяет автоматически уже существующий clipboard installer ALTLINK: его генератор должен отдельно перейти на проверенный 0.2.0 commit/digest и staged CLI. При переносе сохраните token и TLS settings из root-only файлов, текущую БД и units. Не используйте адреса/токены в URL release. Соседний ALTLINK-VPN содержит изменения админки; совместимые unit/integration тесты запускаются отдельно, end-to-end production rollout не заявлен.

Для минимальных Debian/Ubuntu вызывайте новый `sh deploy/install.sh`: он может установить отсутствующий distro Python и зависимости до загрузки Python installer. Прежний генератор с непосредственным `/usr/bin/python3 -I -` этого не умеет; старый уже скопированный скрипт нужно получить заново после обновления генератора. Матрица и --install-deps/--no-install-deps описаны в INSTALLATION.md.

Для history: агентские чтение/запись, HTTPS control transfer и backend import — три разных этапа. last_event_at/event_age_seconds не доказывают задержку импорта. Показывайте свежесть backend ingest отдельно; при отсутствии такого измерения null. 401 → credential/identity; 403 → WAF/permission; 404 → route/deployment; 409 → конфликт profile/map; 5xx → backend/proxy. GET допустимо повторять ограниченно; POST complete-history не повторять автоматически. transport.HistoryClient предназначен для безопасного адаптера и optional health, а не автоматического изменения профиля.

Сохраняйте прежний browser URL через latency_probe_scheme=https, latency_probe_port=44443, latency_probe_path=/ping. Политика публичного firewall — явный opt-in оператора. Не смешивайте browser HTTPS RTT с server TCP или throughput. Проверка loopback IPv6 не подтверждает внешний IPv6/WebView.

User metrics берите из /v1/users/{UUID}/metrics только при available=true и свежем sampled_at. Применение лимита включайте только при exact_user_rate_limit.supported=true. Текущий агент возвращает false/501 и ничего не меняет. При unsupported UI должен показывать причину и отключать кнопку; не вызывайте node-wide traffic_limits. Для эпизодов используйте /v1/alerts/sustained-load, дедуплицируйте node/user/sampled_at при импорте; администраторская рассылка требует отдельной настройки. Для тарифа/миграции нет активных UUID-лимитов в этой реализации; будущий backend обязан сохранять TTL локально, не снимать его tariff sync и отдельно применять на новой ноде.
