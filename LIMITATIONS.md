# Ограничения Domain Activity Monitoring

- Соединение/accepted log event не означает посещение страницы, успешный запрос или завершённое соединение. Фоновое ПО, reconnects, multiplexing и UDP меняют смысл количества событий. Числа — зарегистрированные события, не уникальные посетители и не все сетевые сессии.
- Домен клиентского запроса может отсутствовать при IP destination. ECH скрывает внутренний SNI; outer SNI может принадлежать общему сервису. CDN, shared hosting и несколько доменов на одном IP исключают надёжное восстановление по адресу. DNS/PTR не выполняются. URL paths, HTTPS contents, пароли, cookies, payload не сохраняются.
- Sniffing HTTP/TLS/QUIC зависит от формата/версии/успеха разбора и не гарантирует домен в access.log. Исследование штатного внешнего API и ограничения экспорта приведены в ARCHITECTURE.md. Built-in сборщик не получает SNI/Host/FakeDNS metadata отдельно. Их source labels доступны только доверенному, отдельно реализованному producer с точной корреляцией.
- Не меняются маршруты, destination, sniffing, DNS или настройки Xray. Нет DPI, MITM, сертификатов, packet capture. При отсутствии access.log сбор невозможен. Включение access logging самим оператором имеет отдельную стоимость, которую нельзя назвать нулевой.
- access.log может не содержать inbound tag, email, исходный client IP, outbound или точный destination IP. Без точного user mapping событие не включается в пользовательскую историю. Для inbound-less строк mapping должен явно использовать такой источник; текущий UserMap требует непустой inbound, поэтому они отбрасываются. Peer IP может быть proxy IP. Домен из лога по умолчанию имеет неизвестное происхождение.
- Парсер поддерживает документированные строковые accepted TCP/UDP записи с датой `YYYY/MM/DD HH:MM:SS[.fraction]`, detour и email; fractional часть отбрасывается до секунды. Другая версия/JSON формат требует нового parser adapter. Timezone фиксируется явно; DST/смена timezone требуют корректировки источника. Clock skew и timestamps более 60 секунд в будущем не импортируются.
- Детали доступны 7 дней, агрегаты 30 по умолчанию. Агрегаты сохраняют секунду и измерения кроме client IP/event ID, поэтому при высокой кардинальности размер близок к событиям. Запросы ограничены 2 секундами; большие диапазоны могут вернуть 503. Нужны дисковое квотирование и мониторинг lag в deployment. 30 000 событий в unit test проверяют корректность пакетной обработки, но не доказывают производительность production Xray.
- Бounded polling может отставать от лога: примерно batch_lines/poll_seconds строк в секунду. Пропущенные между polls ротации, copytruncate races, удалённые непрочитанные файлы и аварийный restart после rename могут потерять данные. Anchor выявляет часть rewrites, но одинаковая перезапись файла не всегда обнаружима. Oversized/повреждённые строки и unknown users объединены в счётчике; точная полнота не вычисляется.
- Dedup работает в пределах aggregate retention и стабильного source ID. Для двух независимых источников без общего connection ID нельзя безопасно считать уникальные соединения; не включайте оба для одной сессии. Metadata API не поддерживает позднее обновление существующего события: producer должен отдавать окончательное событие, иначе retry игнорируется.
- Exact domain/connection traffic обычно недоступен в access.log; bytes=null. Счётчики пользователя не распределяются по доменам. Network context — измерение всего выбранного host interface, не доказанный вклад пользователя или домена. Сопоставление по времени не доказывает причину нагрузки.
- Автоматическое удаление очищает рабочие таблицы и WAL (secure_delete, checkpoint), но не исходный log, backups, filesystem snapshots или ранее выгруженные ответы. Purge не гарантирует forensic erasure на SSD. Защита файлов/backup и reverse proxy — обязанность оператора.
- В исходном репозитории не было другого API/auth и Remnawave connector. Поэтому предоставлены общая авторизация самостоятельного сервиса и explicit mapping, без вымышленной интеграции с отсутствующим API. Токен сервисный с доступом к полной истории; tenant/user RBAC должен обеспечивать backend панели.

## Управление сервером

- Административные действия работают только на Linux с opt-in/root и установленными Docker Compose/systemd/tc/sysctl/APT для выбранного действия. Capabilities показывают конфигурацию, а не доказанную доступность tools/privileges. В контейнере metrics могут относиться к namespace, а shutdown/systemctl — не к хосту: запускайте управление на хосте ноды.
- Xray внутри Remnawave Node обновляется с образом ноды, без попытки заменить бинарник внутри контейнера. Для standalone core нужен проверенный operator-installed updater hook. OS kernel update реализован для явно выбранного установленного Debian/Ubuntu metapackage; активация — отдельный reboot.
- Reboot/restart/update прерывают подключения по запросу. Успешный exit команды не доказывает готовность приложения. Обновления не транзакционны; timeout/ошибка может оставить частично применённое состояние. Незавершённые tasks не повторяются автоматически; проверяйте host/package/container state прежде чем повторить.
- TX/RX лимиты применяются ко всему разрешённому NIC; RX policing теряет пакеты. Existing custom qdiscs не заменяются. Только runtime limits; ownership не является автоматическим восстановлением после reboot. Параллельные внешние tc изменения не поддерживаются.
- Memory pressure guard снижает нагрузку самого мониторинга, но не контролирует чужое потребление RAM. vm.panic_on_oom=0 не предотвращает все виды kernel panic/reboot; MemoryMax может убить выбранный процесс. Active logs, unrelated files и свежая история не удаляются; guard может не суметь освободить место и сообщит об этом.
- Emergency deletion укорачивает историю раньше configured retention. Dedup сохраняется, чтобы не воссоздавать удалённые события. SQLite без auto-vacuum может не уменьшить файл; переполненный диск может помешать записи job/error state. Уведомления доступны при работающем процессе через GET /v1/server, без внешней отправки.
- Тесты выполняют fake system runners; реальные privileged Linux команды на компьютере разработки не запускались. Настройки/примеры и процедура проверки: [SERVER_MANAGEMENT.md](SERVER_MANAGEMENT.md).

## Токены и добавление нод

- Новый credential выдаётся основным сервером и переносится в auth.token вручную. UI/хранилище записей основного сервера не входят в текущий агент; предоставлены готовый генератор, библиотечная функция и контракт интеграции. Формат credential не является совместимым токеном API самой Remnawave.
- Каждый токен даёт полный доступ к своей ноде; встроенного per-user RBAC, срока действия и удалённого отзыва через основной сервер нет. Для отзыва замените token в конфиге ноды и перезапустите её или закройте доступ. Повторное использование одного token на нескольких нодах исключает их надёжную изоляцию.
- Bearer credential не шифрует HTTP и не конфигурирует UFW. Через публичную сеть используйте защищённый канал. При config-based credential файл config.json — секрет, его нельзя публиковать в Git или logs. Старые env credentials не действуют параллельно с непустым auth.token.
- UUID из /v1/node проверяется по локальному конфигу, без центрального реестра; backend должен сверять его с ожидаемой записью. Нет автоматического обновления users/log mapping при вставке токена.

## Live и диагностика

- inet_diag adapter — все видимые kernel transport sockets текущего namespace, не логические Xray streams. User/inbound/domain attribution, per-flow bytes/rates/start/duration unsupported; адреса local/peer не объявляются client/destination. Нет PTR/DNS/NAT/timing correlation. TIME_WAIT/CLOSE — observed closed без точного закрытия; исчезновение открытого socket — unknown, UDP presence не активность потока.
- Polling пропускает короткие соединения между samples; полный dump не атомарен на уровне ядра. Budget/permission/timeout/overrun приводят к healthy=false и epoch resync, а не успешному пустому списку. Boot/cursor expiry и bounded ring требуют full resync. Max snapshots=2/TTL и max connections — границы памяти, не SLA производительности.
- Storage alerts имеют version=2, legacy view сохранён отдельно. Выключенный optional log source не создаёт critical; пустой каталог не создаётся. Host/live read-only API переживает startup failure SQLite; privileged mutations без durable audit недоступны. Секреты/raw exceptions/log contents не выдаются источниками диагностики.
- CLI mapping UUID проверяется строго; изменённый mapping/legacy cursor без fingerprint пропускает неподтверждённый backlog с явным gap вместо опасного переатрибутирования. Это не полная историческая привязка по времени; нужны controlled import и прежний mapping.
- Нативные Linux и unprivileged socket tests выполнены на ноде с Xray 26.7.28. Runtime Node 2.7.0/Xray 26.3.27, end-to-end ALTLINK/Panel 2.7.4 и нагрузка 50k реальных VPN streams не подтверждены синтетикой. Текущая P1 socket телеметрия не закрывает application-level attribution. Контракт и evidence: [LIVE_DIAGNOSTICS.md](LIVE_DIAGNOSTICS.md), [TEST_REPORT_LIVE.md](TEST_REPORT_LIVE.md).
## Поставка 0.2.0

Дополнение: новый shell bootstrap ставит недостающие зависимости при --apply /
--install-deps, допускает Python 3.8 и расширенную матрицу Debian/Ubuntu.
Для старых ОС требуются работающие подписанные repositories; проверенный
Debian 11 mirror с 404 не чинится сменой зеркал или отключением trust.
Подробные результаты: TEST_REPORT_DEBIAN_UBUNTU.md.

- Матрица ОС/архитектур является целевой: реальные проверки на amd64 и fixtures не подтверждают arm64/systemd VM/все firewall и Caddy комбинации. Точный перечень — TEST_REPORT_INSTALLATION.md. Полная приёмка всего ТЗ пока не заявлена.
- RemnaNode version discovery поддерживает однозначную release literal в bundled main.js; другие упаковки возвращают null. Нельзя вычислять версию из тега latest, списка зависимостей или единственного встреченного SemVer.
- Установщик не выдаёт публичные сертификаты, не редактирует Caddy и не включает firewall. Сертификаты/renewal и доступ с клиентских устройств проверяет оператор. Неуправляемые legacy units требуют проверенной миграции. Отсутствующий log mount не создаётся автоматически и контейнер не пересоздаётся.
- На проверенной ноде 2026-10-20 найден отсутствующий agent log path при существующем s6 mount; runtime loglevel=none. После попытки реального подключения лог не вырос. Свежая UUID history не подтверждена; пустой лог не подставлялся, Xray/profile не менялись.
- User rates требуют уже работающего Xray StatsService и однозначных пользовательских counters. API/policies автоматически не включаются. Reset/набор счётчиков/gaps приводят к отсутствию данных. Эти totals не дают per-domain/per-flow bytes, TCP и UDP доли или payload.
- UUID shaping для исследованной сборки не подтверждён: GET/POST rate-limit возвращают 501 unsupported. Применение, expiry, persistence, early revoke и migration активного лимита не реализованы без достоверного backend. Общий tc запрещён как fallback. Антиабуз — предупреждения, без автоматических санкций/рассылки.
- Warnings хранятся в bounded RAM (500), сбрасываются при рестарте; для durable admin event history их должен импортировать backend. Правило консервативно: каждый интервал должен превышать порог непрерывно; это строже произвольного скользящего среднего.
- transfer_seconds — время control HTTP-запроса, не измерение backend ingest. Event age при idle не ошибка. Полная latency pipeline требует отдельного времени приёма/обработки на backend.
